Filmic route LUTs — generated, and NOT in use
=============================================

These are the output of a rejected approach (docs/PIPELINE.md, "Tried and rejected"),
kept as its evidence, not because anything reads them.
Nothing in scripts/ references this folder.

What they are
-------------
  f_*.cube    first attempt, 1D. Wrong by construction — see below.
  g_*.cube    3D, with the BT.2020 -> Rec.709 gamut matrix added.
  h_*.cube    g_* plus saturation compensation.

The cubes are gitignored, so a fresh clone has only this file. g_* and h_* are
what scripts/make-filmic-lut.py produces (h_* with --sat); regenerate them from
it and do not hand-edit a .cube. f_* cannot be regenerated: the script always
applies the gamut matrix and writes a 3D cube, and the 1D version that made
f_* was replaced by it rather than kept.

The route
---------
Apple Log -> scene-linear (via Apple's own LogToLin) -> filmic tone curve applied
in LINEAR -> Rec.709. This is the textbook-correct cinema architecture, and the
reason to want it is real: Apple Log carries linear values to 12.0 — about 3.6
stops of headroom above diffuse white — and this footage uses roughly 5.4x of it.
The technical CST compresses all of that away.

Why it did not ship
-------------------
It produced a better TONE response (more density; it used more of the range,
YMAX 943 vs 745) and lost on COLOUR, decisively:

  brick R-B spread    blue sign B/G (spec 1.98)
  4.6                 —              f_* : 1D LUT, no gamut matrix at all. A 3x3
                                     matrix is not expressible as a per-channel
                                     curve, so BT.2020 numbers were being read as
                                     Rec.709 — badly desaturated.
  8.6                 2.05           g_* : matrix added. Still flat.
  16.3                2.45           h_* : saturation compensation added. Brick
                                     recovered, blue went badly off spec.
  17.0                1.97           what ships (Apple's CST + a tone stage)

Apple's CST beats a hand-rolled gamut conversion on both axes at once. The
architecture is right and the implementation is not; a genuinely better version
needs proper gamut mapping, not a naive matrix plus a global saturation
multiplier.

Kept because the next person to have this idea should be able to see how far it
got and where it broke, rather than rebuilding it to find out.
